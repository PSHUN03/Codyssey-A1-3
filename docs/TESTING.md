# 테스트 결과

로컬 정적 서버(`python -m http.server`)에서 브라우저 자동화 도구로 직접 실행하며 확인한
결과다. 표의 "확인 방법"은 실제로 어떻게 검증했는지를 그대로 남긴 것이다.

## 1. 복리 계산기 기능 테스트

| 시나리오 | 입력 | 확인 방법 | 결과 |
|---|---|---|---|
| 정상 입력 | P=5,000,000 / PMT=300,000 / 10년 / 연5% / 월복리 | 실제 화면에서 계산 실행 후 표의 10년차 행 값을 `docs/CALCULATION.md`의 손계산 케이스 3과 대조 | 최종 평가금액 54,819,731원까지 원 단위 일치 ✅ |
| 극단값 — 초기금액 상한 초과 | principal = 2,000,000,000,000 (2조) | `FructusCalculator.validate()` 직접 호출 | "초기 금액은 1조원을 넘을 수 없습니다." 반환 ✅ |
| 극단값 — 수익률 범위 초과 | annualRatePercent = 150 | 위와 동일 | "0% ~ 50% 사이로 입력해 주세요." 반환 ✅ |
| 극단값 — 수익률 소수 입력 | annualRatePercent = 5.5 | 위와 동일 | "수익률은 정수로만 입력할 수 있습니다." 반환 ✅ (0~50 사이의 정수만 허용) |
| 결과 영역 세로 정렬 | 계산기·AI 코치·문의하기 섹션에서 좌우 두 컬럼 하단 정렬 | `getBoundingClientRect()`로 좌/우 컬럼의 `bottom` 값을 비교 | 세 섹션 모두 좌우 컬럼 bottom 값이 소수점까지 일치 ✅ |
| 극단값 — 기간 0 이하 | periodValue = 0 | 위와 동일 | "1 이상의 숫자를 입력해 주세요." 반환 ✅ |
| 극단값 — 음수 입력 | principal = -1000 | 위와 동일 | "0 이상의 숫자를 입력해 주세요." 반환 ✅ |
| 극단값 — 기간 단위별 상한 | periodValue = 1201, unit = month | 위와 동일 | "최대 1,200개월까지 입력할 수 있습니다." 반환 ✅ |
| `hidden` 속성 렌더링 버그 | AI 코치 "다시 시도" 버튼이 초기 로드 시 노출됨 | 스크린샷으로 발견 → 원인 분석(`.btn`의 `display` 속성이 UA `[hidden]` 규칙을 이김) → `css/base.css`에 `[hidden]{display:none!important}` 추가 | 재확인 결과 정상적으로 숨겨짐 ✅ (자세한 경위는 `docs/AI_USAGE_LOG.md` 참고) |

## 2. AI 투자 코치 실패 처리 테스트

| 시나리오 | 방법 | 결과 |
|---|---|---|
| 빈 입력(필수값 누락) | 목표 textarea를 비운 채 제출 | 요청을 보내지 않고 "목표를 한 줄이라도 입력해 주세요." 인라인 오류 + textarea 포커스 ✅ |
| 200자 이상 긴 입력 | 400자 텍스트 입력 후 제출 | 요청을 보내지 않고 "목표 설명은 300자 이내로 입력해 주세요." 오류 ✅ (글자 수 카운터도 실시간으로 300 초과 시 빨간색으로 전환) |
| API 오류(5xx) | 백엔드가 없는 상태(로컬 정적 서버)로 제출 → 서버가 POST를 처리하지 못해 501 반환 | "일시적인 오류입니다. 잠시 후 다시 시도해 주세요." + 재시도 버튼 노출 + 10초 쿨다운 타이머 동작 ✅ |
| 429(요청 과다) | 코드 리뷰로 확인(`statusMessage(429)`) | "요청이 많습니다. 잠시 후 다시 시도해 주세요." 분기 로직 존재 확인 (실제 429는 배포 후 반복 호출로 재확인 예정) |
| 지연/타임아웃 | 코드 리뷰로 확인(`AbortController` 25초) | 25초 초과 시 `AbortError` → "응답이 지연되고 있어요. 다시 시도해 주세요." 분기 확인. 실제 25초 지연 재현은 배포 환경에서 네트워크 스로틀링으로 추가 확인 예정 |
| 쿨다운 | 오류 발생 직후 버튼 상태 관찰 | 제출 버튼이 "10초 후 다시 시도" → 매초 감소 → 0초에 "AI 코치에게 물어보기"로 복귀 ✅ |

## 3. 문의하기 폼 테스트

| 시나리오 | 방법 | 결과 |
|---|---|---|
| 빈 폼 제출 | 이름/이메일/내용을 비운 채 제출 이벤트 발생 | 세 필드 모두 `is-invalid` 클래스 적용 + 필드별 오류 메시지 노출, 요청 전송 안 함 ✅ |
| 잘못된 이메일 형식 | email = "not-an-email" | 백엔드(`api/contact.py`) 단위 테스트: 400 "올바른 이메일 형식을 입력해 주세요." ✅ |
| 정상 입력, 웹훅 미설정 | name/email/message 정상값, `DISCORD_WEBHOOK_URL` 미설정 | 백엔드 단위 테스트: 200 `{ "ok": true, "delivered": false }` — 사용자에게는 접수 성공 메시지 표시 ✅ |

## 5. 접근성 스팟 체크

- 모든 입력 필드에 `<label for>` 연결 확인.
- `aria-current="page"`로 현재 메뉴 표시, `aria-expanded`로 모바일 메뉴/아코디언 상태 노출.
- 결과 영역(`data-result-section`), AI 로딩/결과 영역에 `aria-live="polite"` 적용.
- 키보드 포커스 시 `:focus-visible`로 아웃라인 표시(마우스 클릭 시에는 표시 안 함).

## 6. 알려진 제한 사항

- AI 투자 코치의 "정상 응답(200)" 경로는 실제 Gemini API 키가 필요해 이 문서 작성 시점(로컬 검증 단계)에는 재현하지 못했다. 배포 후 실제 키로 정상 응답 렌더링(카드 UI)을 재확인해야 한다.
- 429/타임아웃 시나리오는 코드 로직 검토로 확인했으며, 배포 환경에서 반복 호출/네트워크 스로틀링으로 추가 실증 검증을 권장한다.
