# AI 코딩 도구 사용 로그

이 프로젝트는 Claude Code(Anthropic의 AI 코딩 CLI)와의 대화로 처음부터 끝까지 개발했다.
아래는 실제 작업 단계와, AI가 생성한 코드에서 실제로 발생한 오류를 발견하고 수정한
과정이다.

## 2. AI가 만든 코드에서 발생한 오류와 수정 과정 (실제 발생 7건)

### 오류 1 — `hidden` 속성이 무시되고 버튼이 계속 보임

- **증상**: `index.html`을 브라우저로 열어 스크린샷을 확인하던 중, AI 코치 섹션의
  "다시 시도" 버튼이 초기 상태(에러가 없는 상태)에서도 계속 화면에 노출됨을 발견했다.
  HTML에는 분명히 `hidden` 속성이 있었다.
- **원인 파악**: 버튼에 적용된 `.btn` 클래스가 `display: inline-flex`를 지정하는데,
  브라우저 기본 스타일시트의 `[hidden] { display: none }` 규칙과 CSS 명시도(specificity)가
  동일(0,0,1,0)하다. 이 경우 캐스케이드 우선순위는 "출처(origin)"로 먼저 갈리는데,
  저자(author) 스타일시트가 사용자 에이전트(UA) 스타일시트보다 항상 우선하므로
  `.btn`이 이겨서 `hidden`이 무력화된 것이었다.
- **수정**: `css/base.css`에 `[hidden] { display: none !important; }` 규칙을 추가해
  어떤 컴포넌트 클래스보다도 `hidden` 속성이 항상 우선하도록 고정했다.

### 오류 2 — learn.html 예시 수치의 계산 오류

- **증상**: `learn.html`의 "시간의 힘"·"수익률 1%p 차이" 섹션에 넣은 예시 금액을
  암산/어림으로 작성했는데, 실제 `js/calculator.js`와 동일한 공식으로 재계산해보니
  여러 값이 어긋났다(예: 35세 시작 30년 후 금액을 "약 2억 9,300만원"이라 썼으나
  실제 계산값은 "약 3억 135만원").
- **원인 파악**: 월 적립금의 미래가치 공식(`(1+i_월)^n` 누적) 암산 과정에서 지수
  계산을 단순화하며 오차가 누적된 것이었다.
- **수정**: Python으로 `calculator.js`와 동일한 함수를 재구현해 정확한 값을 산출하고,
  브라우저에서 `window.FructusCalculator.calculate()`를 직접 호출해 그 값과 다시
  대조한 뒤 `learn.html`의 모든 예시 수치를 교체했다.

### 오류 3 — 불필요한 git 로컬 설정 변경

- **증상**: `git init` 직후 커밋을 위해 `git config user.email`을 로컬로 설정했는데,
  이는 "git 설정을 임의로 바꾸지 않는다"는 안전 수칙에 어긋나는 행동이었다.
- **원인 파악**: 커밋이 실패할 것을 예상해 방어적으로 설정을 추가했지만, 실제로는
  `git config --global --list`로 확인한 결과 전역 설정에 이미 올바른 사용자 정보
  (`PSHUN03` / `hunhun345345@gmail.com`)가 있어 불필요한 변경이었다.
- **수정**: `git config --unset user.email`로 로컬 오버라이드를 즉시 제거해 전역
  설정을 그대로 사용하도록 되돌렸다.

### 오류 4 — 본문 텍스트가 한쪽으로 쏠리는 레이아웃 불균형 (사용자 리포트)

- **증상**: 실제 사용자가 배포 전 미리보기를 확인하고 "웹사이트가 한쪽으로 치우쳐져
  가독성이 떨어진다"고 지적했다. 실제로 넓은 화면(1920px)에서 `.container`의 좌우
  여백은 동일했지만, 히어로 제목/부제 안쪽 텍스트가 컨테이너보다 훨씬 좁은
  `max-width`(18ch, 56ch)로 추가 제한되어 있어 텍스트가 왼쪽에 붙고 오른쪽에
  600px 넘는 빈 공간이 남아있었다.
- **원인 파악**: `getBoundingClientRect()`로 직접 측정해, 컨테이너 자체는 정확히
  가운데 정렬되어 있지만(좌우 여백 거의 동일) 그 안의 `<h1>`이 `max-width: 18ch`
  때문에 이미 넣어둔 `<br>` 줄바꿈과 충돌하며 "확인하세요"가 "확인하세"/"요"로
  쪼개지는 것까지 확인했다 — 여백 불균형과 단어 어색한 줄바꿈이 같은 원인이었다.
- **수정**: 히어로/본문(prose)/FAQ 목록 등에서 불필요한 `ch` 단위 폭 제한을 제거해
  컨테이너 폭을 그대로 채우게 하고, 문의 폼처럼 의도적으로 좁아야 하는 요소는
  `margin-inline: auto`로 가운데 정렬해 좌우 여백을 동일하게 맞췄다. 또한
  `body`에 `word-break: keep-all`을 전역으로 추가해 앞으로도 한글 단어가
  음절 단위로 쪼개지지 않도록 근본 원인을 제거했다.

### 오류 5 — 배포 후 AI 코치가 항상 오류를 반환 (모델 단종)

- **증상**: Vercel에 배포하고 `GEMINI_API_KEY`까지 정상 등록한 뒤 실제로 "AI 코치에게
  물어보기"를 눌러보니 매번 "일시적인 오류입니다" 메시지만 떴다. 코드 자체(검증
  로직, 요청 본문 구성)에는 문제가 없어 보였다.
- **원인 파악**: `api/coach.py`가 호출하던 모델명 `gemini-2.0-flash`가 원인이었다.
  웹 검색으로 확인한 결과 Google이 2026년 6월 1일부로 Gemini 2.0 Flash / Flash-Lite
  모델 서비스를 종료했다 — 즉 존재하지 않는 모델을 호출하고 있었던 것이다. Gemini API가
  404를 반환하면 우리 코드는 이를 `HTTPError`로 잡아 사용자에게는 뭉뚱그린 "일시적인
  오류입니다"로만 보여주도록 설계되어 있어(보안상 상세 원인은 숨김), 화면만 봐서는
  원인을 알 수 없었다.
- **수정**: 현재 Gemini API 문서 기준 정식(GA) 모델인 `gemini-2.5-flash-lite`로
  교체했다. 이 경험을 통해 "AI API 모델명은 시간이 지나면 단종될 수 있으므로,
  화면에 보이는 오류 메시지만으로 원인을 추측하지 말고 Vercel 함수 로그나
  외부 API 상태를 함께 확인해야 한다"는 점을 반영했다.

### 오류 6 — AI 코치가 배포 이후 단 한 번도 성공한 적이 없던 진짜 원인

- **증상**: 오류 5를 고치고 재배포까지 했는데도 여전히 즉시 실패했다. Vercel 로그를
  같이 확인해보니 실행 시간이 6~9ms로 비정상적으로 짧고 "External APIs: No outgoing
  requests" — Gemini API를 호출하기도 전에 죽고 있다는 뜻이었다. 환경변수(API 키)도
  Production/Preview에 정상 등록돼 있었고 재배포도 새로 만들어졌는데 동일했다.
- **원인 파악**: 로컬에서 실제 HTTP 서버를 띄워 동일한 요청을 재현하고 예외를
  강제로 출력해보니 `KeyError`가 `_build_prompt()` 안, 정확히는 `str.format()`
  호출 지점에서 발생하고 있었다. 프롬프트 문자열 안에 AI에게 보여줄 JSON 스키마
  예시를 `"{\n  \"diagnosis\": ...\n}"` 형태로 그냥 넣어뒀는데, `.format()`은
  문자열 전체에서 `{...}`를 전부 "여기에 값을 채워라"는 자리표시자로 해석한다.
  즉 스키마 예시의 중괄호까지 자리표시자로 오인되어 매번 예외가 났던 것이다.
  이 버그는 `api/coach.py`를 처음 작성한 시점부터 있었기 때문에, API 키나
  모델명이 아무리 정확해도 AI 코치는 배포 이후 단 한 번도 실제로 Gemini를
  호출한 적이 없었다 — 오류 5에서 의심했던 "환경변수 미반영"은 결과적으로
  곁가지였고, 진짜 원인은 이 코드 버그였다.
- **수정**: 스키마 예시 부분의 리터럴 중괄호를 `.format()` 규칙에 맞게 `{{`, `}}`로
  이스케이프했다. 가짜 API 키로 로컬 재현 테스트를 다시 돌려, 이번엔 실제로
  Gemini API까지 요청이 나가고(가짜 키라 502로 정상적으로 거절당함) 정상 흐름을
  탄다는 것까지 확인한 뒤 수정했다. **교훈**: "환경변수/배포 설정이 맞는데도 계속
  실패한다"고 겉으로 보이는 문제일수록, 설정을 다시 의심하기 전에 실제 코드를
  로컬에서 강제로 재현해 정확한 예외 스택트레이스를 먼저 확인하는 것이 훨씬
  빠르다.

### 오류 7 — "처음 한 번만 성공하고 이후 계속 실패"

- **증상**: 모델을 `gemini-3.6-flash`로 바꾼 뒤 첫 요청은 성공했는데, 그 다음부터는
  계속 실패했다. 코드를 바꾼 것도 없는데 결과가 매번 달라지는 상황이었다.
- **원인 파악**: 배포 URL의 `/api/coach`를 직접 여러 번 호출해 응답을 수집했더니
  `ValueError: no-json-found`가 나왔다. Gemini 호출 자체는 성공(11초 소요)했지만,
  돌아온 텍스트에서 JSON을 찾지 못한 것이다. 원인은 Gemini 3 계열이 답변 전에
  소비하는 **thinking 토큰이 `maxOutputTokens` 예산에서 함께 차감**된다는 점이었다.
  생각이 길어지면 JSON이 닫히기 전에 응답이 잘려버리는데, 생각 길이는 매번 다르므로
  **성공/실패가 확률적으로 갈렸다.** "한 번만 성공"은 우연히 예산 안에 끝난 경우였다.
- **수정**: 운에 맡기지 않도록 세 겹으로 차단했다.
  1. `responseMimeType: "application/json"` + `responseSchema` — 프롬프트로 "JSON만 달라"고
     *부탁하는* 대신 API 차원에서 스키마에 맞는 순수 JSON만 나오도록 강제
  2. `thinkingLevel: "minimal"` — 내부 추론을 최소화해 예산을 실제 답변에 사용
  3. 프롬프트에 분량 제한(각 항목 최대 2문장 등) 명시 — 생성 토큰이 줄어 응답도 빨라짐
  덧붙여 `thinkingLevel`은 Gemini 3 전용 옵션이라 모델에 따라 거부될 수 있어,
  400이 오면 **그 옵션만 빼고 자동 재시도**하도록 방어 로직을 넣었다.
- **교훈**: "가끔 되고 가끔 안 되는" 증상은 코드의 분기 문제가 아니라 **외부 응답이
  매번 달라지는 구조** 때문일 수 있다. 이럴 때는 한 번 호출해 보고 판단하지 말고
  여러 번 반복 호출해 패턴을 봐야 원인이 드러난다.

## 3. 참고 — 이 로그 자체도 개발 과정의 일부

이 문서는 실제 작업을 진행한 Claude Code 세션의 대화 기록을 바탕으로 작성했으며,
가상의 시나리오가 아니라 이 저장소의 커밋 이력(`git log`)과 1:1로 대응한다.
